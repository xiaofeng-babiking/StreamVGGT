1. Overview

This page is a runbook for launching VGGT → StreamVGGT distillation training across multiple nodes. The orchestrator (svggt_orch) is a Python package that uses asyncssh to fan-out docker run commands to a pool of worker nodes, each running accelerate launch inside a container that bind-mounts the shared /jfs-resident uv venv.

What you get out of one launch:

  • One training job with a stable world size (no elastic membership).
  • Per-rank logs streamed back to the head node via SSH.
  • A live TUI dashboard with GPU utilization, IB throughput, and a heartbeat staleness signal.
  • TensorBoard wired to the shared checkpoints/<exp_name>/logs directory.
  • Auto-resume from checkpoint-last.pth if the job is restarted.
Why this exists The upstream accelerate launch --multi_gpu only handles a single node. Multi-node DDP requires coordinated launches with matching --machine_rank, consistent MASTER_ADDR/PORT, NCCL config aware of the IB fabric, and a way to discover idle GPUs across the pool. This orchestrator wraps all of that in seven subcommands.

A Phase A — Bootstrap

One-shot setup, runs on the head node. Idempotent and safe to re-run. This is the only phase you typically have to repeat after a dependency change in pyproject.toml or uv.lock.

Run

$ cd /jfs/jing.feng/codebases/StreamVGGT
$ ./scripts/bootstrap_venv.sh

What it does

  1. Checks uv is on $PATH (exit 1 with install URL if missing).
  2. Verifies /jfs has ≥ 5 GB free (exit 2 if not — JuiceFS is shared, full disk hits everyone).
  3. Takes flock -n .venv.lock so a peer node can't race the same sync (exit 3 if held).
  4. Sets UV_PYTHON_INSTALL_DIR=<repo>/.uv-python so the Python interpreter lives on /jfs (bind-mountable into every worker container).
  5. Detects + deletes any stale .venv whose bin/python symlinks outside that directory (would crash inside docker with exit 127).
  6. Runs uv sync --extra orchestrator --group dev.
  7. Asserts the venv's bin/python resolves under .uv-python/ (post-sync portability gate).
  8. Sanity-checks: python -c "import torch, accelerate, asyncssh, click, yaml, rich".
Why UV_PYTHON_INSTALL_DIR matters uv's default is ~/.local/share/uv/python/..., which sits on local /home (not /jfs). Worker containers bind-mount only /jfs, so the venv's shebang #!/home/.../cpython-3.11/bin/python3.11 becomes unreachable inside the container — kernel exec returns "required file not found" and the worker exits 127. Installing the interpreter onto /jfs/.../.uv-python/ resolves identically on every node.

Re-running is cheap

The wheel cache at ~/.cache/uv/ survives rm -rf .venv. A re-sync typically takes 2–5 min vs. 20 min for the cold case. To enforce "no network fetch at all": 

$ UV_OFFLINE=1 ./scripts/bootstrap_venv.sh
JuiceFS first-run latency Sync time is dominated by JuiceFS write throughput; the first bootstrap typically takes 60–120 s longer than re-runs. The page cache warms after the first run, so subsequent imports inside containers are much faster.

B Phase B — Discover

Probe every candidate host in workflows/cluster.yaml#candidate_hosts over asyncssh, capture per-GPU memory usage from nvidia-smi, and write the manifest of "currently idle" GPUs to workflows/nodes.json. Unreachable hosts are skipped without aborting.

Run

$ export SSH_PASSWORD='...'                  # only if cluster.yaml uses password auth
$ ./scripts/svggt-orch discover --dry-run    # prints plan, no SSH
$ ./scripts/svggt-orch discover              # real fan-out
SSH_PASSWORD must be in every shell that runs svggt-orch The loader resolves ${SSH_PASSWORD} at load time, so even --dry-run needs it set. Per-invocation form works too: SSH_PASSWORD='...' ./scripts/svggt-orch discover. Missing the env var raises RuntimeError: cluster.yaml references env var ${SSH_PASSWORD} but it is not set — clear, not silent.

What it does (per host, in parallel)

  1. Open asyncssh connection (connect_timeout_s from cluster.yaml).
  2. Run nvidia-smi --query-gpu=index,memory.used --format=csv,noheader,nounits.
  3. Filter GPUs with memory.used < idle_threshold_mib (default 500 MiB).
  4. Skip the host if it has fewer than min_idle_gpus_per_node idle GPUs (default 1).
  5. Pull the IPoIB address via ip -j addr show ibs110 for later NCCL bootstrap.

Idempotent and re-runnable discover overwrites workflows/nodes.json on every run. If a peer steals GPUs between discover and launch, the launcher will use whatever was current at discover time — re-run discover before launch if you suspect drift.

C Phase C — Launch

Compute a LaunchPlan from nodes.json + cluster.yaml, write the job manifest, then asyncssh-fan-out a docker run -d to every node. Atomic abort on any failure.

Run

$ export SSH_PASSWORD='...'  # or rely on identity_file in cluster.yaml

# Dry-run (offline): prints the plan; doesn't SSH or start docker
$ ./scripts/svggt-orch launch --dry-run --exp-name StreamVGGT_alpha0.1_lr1e-5_nog

# Real launch — uses cluster.yaml#train.config_name (e.g. 'train')
$ ./scripts/svggt-orch launch --exp-name StreamVGGT_alpha0.1_lr1e-5_nog

# Override the hydra config without editing cluster.yaml:
$ ./scripts/svggt-orch launch --config-name train_smoke --exp-name SmokeRun
$ ./scripts/svggt-orch launch --config-name finetune    --exp-name VGGT_FT
Three "config" levels, three flags
  • --config workflows/cluster.yaml — orchestrator cluster manifest (group-level, before subcommand)
  • --config-name train_smoke — Hydra config under config/ (launch-level)
  • --exp-name SmokeRun — checkpoint/log subdir name (launch-level)
Dry-run output now includes config_name: as a row so the rendered plan is a full reproducibility receipt.

       --env MAIN_PROCESS_IP=10.10.100.5 --env MAIN_PROCESS_PORT=26902 \
       --env CONFIG_NAME=train --env CUDA_VISIBLE_DEVICES=0,1,2,3,4,5 \
       --env NCCL_IB_HCA=mlx5_1 --env NCCL_IB_DISABLE=0 \
       --env NCCL_SOCKET_IFNAME=bond0 --env NCCL_ASYNC_ERROR_HANDLING=1 \

       --env NCCL_NET_GDR_LEVEL=PIX \
       "${DOCKER_RUN_FLAGS[@]}" \
       babiking/ubuntu:12.8.1-cudnn-devel-ubuntu24.04 \
       /workspace/scripts/worker_entry.sh
Why --gpus '"device=…"' uses nested quotes Some docker engines parse the bare form --gpus device=0,1,2 as setting both Count (from list length) and DeviceIDs, then reject with: 
docker: Error response from daemon: cannot set both Count and DeviceIDs on device request.
The outer single quotes survive the remote shell parsing, leaving docker holding "device=0,1,2" as one literal argument that its parser recognizes as device-IDs only. The orchestrator builds this form in _build_docker_cmd and has a regression test (test_gpu_flag_uses_nested_quoting) pinning the exact output.

Inside the container — worker_entry.sh

  1. Validate required env vars (exit 1 if any missing).
  2. mountpoint -q /jfs + touch test (exit 11 if /jfs not writable as host UID).
  3. Activate /workspace/.venv via VIRTUAL_ENV + PATH (exit 12 if missing).
  4. Start background nvidia-smi dmon -s pucvmet -d 2 -o T → workflows/jobs/<jobid>/dmon-<host>.csv.
  5. cd /workspace/src; exec accelerate launch --multi_gpu --num_machines $N --machine_rank $R ... ./train.py --config-name $CONFIG_NAME.

Expected output (head)

launch: starting svggt-20260525-162300 on 6 nodes
launch: started ok. Manifest: workflows/jobs/20260525-162300/manifest.json

D Phase D — Training (steady state)

Once accelerate launch spawns the per-GPU processes inside each container, the training loop is the same code that runs in the single-node case (src/train.py, train_one_epoch). The only difference: world size 36 instead of 1, and one extra line that writes a heartbeat file.

Heartbeat write (added in this branch — train.py)

                for name, val in loss_details.items():
                    ...
                    log_writer.add_scalar("train_" + name, val, step)

                # Heartbeat for the orchestrator's hang watchdog.
                Path(args.output_dir, "heartbeat").write_text(
                    f"{time.time()} {step}\n"
                )

Cadence: written every print_freq steps (10 by default) on rank 0 only. The orchestrator's monitor polls mtime(<exp>/heartbeat) and flips to a red banner if it goes stale for > 600 s. This catches the "rank silently hung; NCCL won't timeout for 100 minutes" failure mode.

Datasets live in-place on /jfs Workers read training data straight from /jfs/Data_4DFF/train_data/<dataset>/ via the bind-mount — no symlinks, no preprocessed mirrors. Three dataset loaders were patched to handle this cluster's data layout quirks (BlendedMVS/MegaDepth use .safetensor camera params, OmniObject3D has an extra category nesting level). See §13 Cluster-specific loader patches for details.

NCCL_ASYNC_ERROR_HANDLING=1 is doing real work Without it, a dying rank leaves peers blocked on the next all-reduce until the 6000 s (100 min) timeout fires. With it, peers see the missing rank within seconds and abort cleanly. This env var is set by default by the orchestrator's nccl_env.build_nccl_env; do not disable it without understanding the silent-hang implications.

13. Cluster-specific loader patches

This cluster's preprocessed training data deviates from upstream's expected layout in two ways, both rooted in a parallel preprocessing pipeline that wasn't synced with the dust3r repo's datasets_preprocess/ scripts. Rather than re-preprocess hundreds of GB on a 96 %-full /jfs, the loader code learned to read what's actually there.

Per-frame cam params serialized as .safetensor instead of .npz BlendedMVS, MegaDepth Loaders accept data_format='auto' | 'npz' | 'safetensor'. Default 'auto' tries .npz first then falls back; both formats yield structurally equivalent dicts. 77ba367
Extra <category>/<instance> nesting under ROOT OmniObject3D OmniObject3D_Multi accepts nested_layout='auto' | True | False. 'auto' uses leaf markers (rgb, depth, cam subdirs) to detect depth. Also: scale.json is now optional, falling back to scale=1.0 per scene. d8132a9

Declarative config (explicit kwargs in train_distribute.yaml)

The cluster's choices are spelled out in the yaml rather than relying on auto-detection, so the config doubles as documentation: 

dataset8:  BlendedMVS_Multi(..., ROOT='/jfs/.../blendedmvs',  data_format='safetensor', ...)
dataset9:  MegaDepth_Multi(..., ROOT='/jfs/.../megadepth',   data_format='safetensor', ...)
dataset12: OmniObject3D_Multi(..., ROOT='/jfs/.../omniobject3d/train', nested_layout=True, ...)
Why explicit kwargs instead of 'auto' Auto-detection is a defensive default that keeps upstream-format data loadable by the same code. Pinning the value in the yaml is a stronger declaration of intent: a stray .npz dropped next to the .safetensor files won't change behavior, and a future re-preprocess flips behavior via a single visible toggle, not via filesystem state.
